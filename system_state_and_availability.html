Equipment Monitor: State Collection and Availability Logic

Last updated: 2026-06-22

1) High-level flow

  1. Collector loads config.yaml and creates one OPC client per PLC.
  2. Each client subscribes to a minimal set of state tags per equipment module (EM).
  3. Incoming value changes drive an EM state tracker.
  4. Tracker writes:
    • em_availability_raw (signal snapshots + active sequence context)
    • em_current_step (live active step per EM)
    • step_event and fault_event on sequence transitions/fault edges
    • em_down_event when availability drops
  5. Dash pages compute availability/timelines from these DB tables.

2) OPC tags used for state transitions

Each EM uses its configured base path: {em_db_path} (with Siemens DB name quoting applied).

3) Availability state model

Tracker derives one of four SEMI E10-style states from EM-level signals + active-sequence context:

Derived stateCondition
unscheduled_downfault = true
unscheduled_downautomatic = true and active sequence is non-production (e.g. Home)
productiveautomatic = true and running = true and no fault and no non-production override
standbyautomatic = true and running = false and no fault and no non-production override
manualElse (typically not in automatic with no fault)

Raw snapshots are written to em_availability_raw with:

  • automatic, fault, running
  • active_seq, active_is_production
  • timestamp ts (monotonic per EM)

4) Down-event reason logic (why downtime happened)

4.1 Open trigger

A row in em_down_event opens when derived state enters down/manual (sticky root-cause model).

4.2 Reason attribution precedence

  1. Step fault edge (stepControl[N-1].faulted) -> reason type step_fault.
  2. Manual/idle transition:
    • If interlock snapshot shows failed conditions -> reason type interlock with parsed condition text.
    • If interlocks are healthy -> reason type manual and reason text Manual mode.
  3. Non-production active sequence -> reason text like Non-production sequence active (N).

4.3 Placeholder handling

Placeholder strings are not intended to persist. If async enrichment cannot resolve before close, close-out finalization rewrites to a concrete value (typically Manual mode or EM fault active (interlock details unavailable)).

5) Availability calculation shown in the app

From SQL interval rollups over em_availability_raw:

Availability % = (productive + standby) / (productive + standby + unscheduled_down) * 100

manual time is excluded from denominator (SEMI E10 non-scheduled time treatment).

6) Quick PLC audit checklist

  • Watch .status.mode.automatic, .status.running, .status.alarm.fault, .status.activeSequence together.
  • Watch .interlock struct condition array fields (ok + description).
  • If machine idles and interlock conditions remain healthy, downtime will classify as Manual mode.
  • If one or more interlock conditions drop, their descriptions are used as the down-event reason.
